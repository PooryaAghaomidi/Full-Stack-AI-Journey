## What are Design Patterns?

**Design patterns** are **proven, reusable solutions** to common software design problems. They provide a blueprint for solving recurring issues in software development without reinventing the wheel.

- Patterns are **not code** but conceptual solutions.  
- They **standardize approaches** so multiple developers can understand and maintain code easily.  
- Example: Using a Singleton pattern to ensure a class has **only one instance**, like a logging service.

**Key Points:**

- Patterns are language-agnostic but can be implemented in any programming language.
- They improve **communication** between developers using standard terminology.

---

## Benefits of Design Patterns

1. **Maintainability**  
   - Patterns make code easier to read, modify, and debug.  
   - Example: A Factory pattern separates object creation, reducing changes in multiple places.

2. **Reusability**  
   - Encapsulates solutions that can be reused across projects.  
   - Example: Observer pattern can be reused for UI updates in multiple applications.

3. **Scalability**  
   - Patterns provide structured ways to scale applications.  
   - Example: Using a Proxy pattern to control access to resources as the system grows.

4. **Communication**  
   - Patterns create a **shared vocabulary** among developers.  
   - Saying "Let's use a Singleton here" immediately conveys the intention.

5. **Best Practices**  
   - Patterns represent **tried-and-true solutions** adopted by the software engineering community.

## Categories of Design Patterns

Design patterns are typically divided into three main categories:

### Creational Patterns

- Deal with **object creation**.  
- Help in creating objects **without exposing the instantiation logic**.  
- Examples: Singleton, Factory Method, Abstract Factory, Builder, Prototype.  

### Structural Patterns

- Deal with **object composition** and relationships.  
- Focus on how objects are connected to form larger structures.  
- Examples: Adapter, Decorator, Proxy, Composite, Facade, Flyweight.  

### Behavioral Patterns

- Deal with **object interaction and communication**.  
- Help manage **algorithms, responsibilities, and communication** between objects.  
- Examples: Observer, Strategy, Command, State, Template Method, Iterator, Mediator, Chain of Responsibility.

---

## How to Choose the Right Pattern

1. **Identify the Problem Type**
   - Creation? → Creational pattern  
   - Structure? → Structural pattern  
   - Behavior/interaction? → Behavioral pattern  

2. **Understand the Context**
   - Consider **performance, scalability, and maintainability** requirements.

3. **Look for Reusability**
   - Patterns shine when the solution may be **reused in multiple places**.

4. **Start Simple**
   - Avoid over-engineering. Only use a pattern if it **solves a real problem**.

5. **Combine Patterns if Needed**
   - Often, professional systems use **multiple patterns together** (e.g., Factory + Observer).

## Anti-Patterns to Avoid

**Anti-patterns** are common but **poor solutions** that may seem correct initially but lead to maintenance problems.

### Examples

1. **God Object**
   - One class does **everything** → hard to maintain.  
   - Solution: Break it into multiple classes using patterns like **Facade** or **Strategy**.

2. **Spaghetti Code**
   - Tangled, unstructured code.  
   - Solution: Use **Structural and Behavioral patterns** to organize relationships.

3. **Golden Hammer**
   - Applying a familiar pattern everywhere, regardless of its suitability.  
   - Solution: Analyze the problem, pick the **pattern that fits**.

4. **Copy-Paste Programming**
   - Duplicating code instead of reusing it.  
   - Solution: Use **Creational patterns** and functions for reuse.

## Example: Singleton Pattern (Concept Preview)

```python
class Singleton:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super(Singleton, cls).__new__(cls)
        return cls._instance

# Usage
logger1 = Singleton()
logger2 = Singleton()
print(logger1 is logger2)  # True, only one instance exists
```

Use Case: Logger service, configuration manager, database connection pool.

Demonstrates how design patterns provide a standard, reusable solution.
